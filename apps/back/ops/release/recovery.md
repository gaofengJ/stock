# 发布与恢复

合并 `master` 会构建提交 SHA 对应镜像并自动执行 `deploy.sh`。首次发布会停用旧后端进行备份和迁移，存在维护时间；前端仍可打开，但后端请求在此期间不可用。不要在业务高峰合并。

## 发布记录

生产配置由发布任务生成，保存在 `/opt/stock-release/packages/<SHA>/release/runtime.env`（权限 600），不再写入镜像或构建缓存。数据库命令和应用容器均通过只读挂载 `/run/stock/runtime.env` 与 `APP_ENV_FILE=/run/stock/runtime.env` 加载配置。手工恢复时必须使用对应版本的配置文件和同样的挂载参数；仍被运行或保留的回滚容器引用的发布目录不可删除。临时备份客户端配置与此长期运行配置是两个文件。

`timings.log` 记录镜像拉取、预检、刷新暂停、停服、备份导出压缩、完整性校验、校验和、迁移、启动和接口验证的独立耗时及成功/失败状态，Actions 日志同步输出。备份完成时还输出压缩文件实际字节数，便于区分磁盘预算与实际备份大小。

每次发布保存在 `/opt/stock-release/runs/<时间>-<SHA>/`，仅 root 可读：预检、迁移前后数量、备份及校验和、旧容器配置与镜像 ID、原刷新程序和发布阶段。数据库凭据文件只在备份期间存在并在退出时删除。备份包含业务数据，不得提交到 Git 或上传公开 Actions 产物。

预检不写数据库。它要求 InnoDB 表、正确的现有索引定义。磁盘预算分为完整备份（表及索引总大小的两倍）、待执行迁移的工作空间（涉及表大小的两倍）和 1 GiB 余量。目前只有已审核的登录动态迁移按账户相关表计算；历史迁移、未配置的新迁移保留整库工作空间，仍等同原来的四倍加 1 GiB 门槛。没有待执行迁移时仍保留完整备份预算。预检输出 `spaceBudget` 明细，完成 gzip 备份与校验后还会再次检查迁移空间。该估算不能替代磁盘监控；空间不足立即终止，不删除以前的备份来强行发布。

## 失败分界

- 拉取、预检失败：旧服务继续运行。
- 停服后备份失败：启动旧服务，恢复刷新原来的暂停状态。
- 开始执行迁移后失败：DDL 可能已提交，旧服务保持停止，新服务如已启动也会停止。刷新保持暂停，发布返回失败。不要直接重启旧容器：新唯一索引与旧版追加写入逻辑不兼容。

## 优先修复并继续新版

读取失败目录的 `phase`、`migration.jsonl` 及错误日志，核对 `old-container-name` 和镜像 SHA。确认没有其他发布或写入进程后，使用相同 SHA 镜像运行 `node ops/release/database.cjs preflight`，修复明确的失败原因，再运行 `migrate` 和 `verify`。迁移可重跑，重复行备份不会被覆盖；索引定义错误时必须人工核实，不能删除索引后盲目重试。

验证通过后按 `deploy.sh` 中的同一网络映射、端口、日志挂载和 `SYNC_ON_STARTUP=false` 启动新版，并运行 `node ops/release/smoke.cjs`。若失败现场已有名为 `stock-back` 的新版容器，先保留其日志并改名，勿覆盖旧版本。恢复刷新前先确认维护开始时是否已由用户主动暂停。

## 必须回退旧版时

1. 保持维护状态，确认所有业务写入和测试刷新均已停止。保存故障库的额外备份，避免丢失发布之后的数据。
2. 校验原始备份的 SHA-256 和 gzip 完整性。先在本地隔离 MySQL 5.7 中将备份恢复到独立空库，核对原表数量、关键日期及查询结果；不要在资源有限的生产服务器另起全量副本，禁止直接将 `DROP TABLE` 形式的备份导入仍有写入的生产库。
3. 由运维明确接受回退时间点后，在维护窗口恢复原库，或使用已验证的恢复库并修改旧容器的数据库配置。核查新版本独有的任务及策略表，不将它们误认为旧版同步成功证明。
4. 使用记录中的旧镜像、端口和挂载启动旧服务，验证接口；恢复对应旧刷新脚本及先前暂停状态。

`migration:revert` 不恢复去重删除的行，不是整库回退方案。本地演练只会恢复隔离数据库，不会自动执行上述生产回退。

本地恢复演练的顺序如下。客户端配置文件应只允许当前用户读取，并明确指向本地隔离实例；备份未包含 `CREATE DATABASE` / `USE stock`，恢复库名由客户端指定。空库应预先创建，字符集使用 `utf8mb4`。

```sh
gzip -t stock.sql.gz
sha256sum -c stock.sql.gz.sha256
set -o pipefail
gzip -dc stock.sql.gz | mysql --defaults-extra-file=/path/to/local-only.cnf stock_recovery
```

恢复后逐表比较 `COUNT(*)` 与迁移前快照，确认旧版不含新增业务唯一索引，再验证关键日期查询。不要仅凭导入进程退出成功就判定恢复可用。

## 日常行为

生产默认不在启动时发起外部同步，部署验证成功后使用 `database.cjs enqueue-market` 创建持久化两年补齐任务。20:30正常同步、每15分钟重试至22:00核对、次日07:30复核；历史批次每次最多3日，批次释放写锁。启用 `SYNC_ON_STARTUP=true` 时恢复不受晚间窗口限制。

两年范围保留更早数据，先复用已有完整原始行情，再补指数和汇总。主动删除保护不会被自动恢复。测试库使用新版 `history-refresh.cjs` 按业务键合并，保留同步状态和保护日期；必须和 `refresh.py`、`refresh.cjs` 一起升级，不能恢复为旧版30日整表覆盖。
